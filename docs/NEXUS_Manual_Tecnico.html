I. Arquitectura y programación orientada a objetos

Propósito y funcionamiento general

NEXUS es un sistema interactivo de simulación y exploración basado en consola que aplica los principios de la Programación Orientada a Objetos (POO) en C#. El sistema orquesta entidades (Usuario, Enemigo, EntidadIris), la topografía dinámica mediante la clase Realidad y AtlasRealidades, y la manipulación de estado persistente serializado en formato JSON (DatosPartida).

Estructura del proyecto y responsabilidades

  • Capa de Control (Program.cs): Contiene el bucle principal (while (conectado)), maneja el motor de renderizado ANSI y orquesta la lógica del negocio.
  • Modelos de Entidad (Domain): Clases como Entidad, Usuario, Enemigo y EntidadIris encapsulan el estado (vida, energía, daño) y las reglas de negocio (validaciones de límites).
  • Modelos de Entorno: Realidad encapsula la matriz del mapa y sus reglas topográficas.

Diagrama de clases y relaciones entre objetos

Diferencias entre programación estructurada y POO

Si NEXUS fuera estructurado (ej. C clásico), la Energia sería una variable global, propensa a ser modificada accidentalmente por cualquier función del mapa. Gracias a la POO, la lógica de validación convive directamente con los datos dentro del objeto Usuario. El bucle de Program.cs no necesita saber cómo se calcula el límite de energía, simplemente se lo delega al objeto cadete.

II. Fundamentos de clases y objetos

Clases, objetos e instanciación

Una clase es la plantilla (ej. class Usuario). El objeto es el espacio físico reservado en la memoria Heap que nace al usar la palabra reservada new. En NEXUS, instanciamos al jugador tras verificar su biometría:

// Instanciación (nacimiento del objeto)
cadete = new Usuario(nombreIngresado, edadIngresada);
realidadAsignada = new Realidad();

Atributos, campos, propiedades y encapsulamiento

NEXUS aplica un fuerte encapsulamiento para proteger la integridad del estado. No se usan variables públicas desnudas. Observa el control en la clase Usuario:

private int _energia; // Campo (Field) - Privado, oculto al exterior
public int Energia  // Propiedad (Property) - Expuesta con reglas estrictas
{
    get { return _energia; }
    set { _energia = value >= EnergiaMax ? EnergiaMax : (value < 0 ? 0 : value); }
}

Si el jugador pisa una mina que resta 50 de energía y solo tenía 10, la propiedad impide que la energía baje de 0, asegurando que el estado matemático nunca se rompa.

Constructores, sobrecarga y uso de this

NEXUS utiliza sobrecarga de constructores en la clase Usuario. Se requiere un constructor vacío (public Usuario() { }) obligatoriamente para que el motor de guardado JsonSerializer.Deserialize pueda reconstruir el objeto. Sin embargo, para crear un jugador nuevo, usamos la sobrecarga parametrizada, aplicando this para distinguir entre variables de clase (campos/propiedades) y parámetros:

public Usuario(string nombre, int edad)
{
    this.Nombre = nombre; 
    this.Edad = edad; 
    this.EnergiaMax = 10; 
    this.Energia = EnergiaMax;
    // Inicialización de listas...
}

III. Herencia, polimorfismo e interfaces

Clases base y derivadas (Reutilización de código)

En NEXUS, Usuario y Enemigo comparten características (vida y daño). En lugar de duplicar variables, ambas heredan de Entidad (la clase base).

class Entidad {
    public int VidaMax { get; set; }
    public int Vida { get; set; }
}
class Usuario : Entidad { /* Hereda Vida y VidaMax automáticamente */ }
class Enemigo : Entidad { /* Hereda Vida y VidaMax automáticamente */ }

Polimorfismo: virtual y override (Ejemplo complementario)

Actualmente el daño de Entidad es pasivo. Si quisiéramos que cada entidad ataque de forma distinta, aplicaríamos polimorfismo dinámico en NEXUS. Modificaríamos la base así:

class Entidad {
    public virtual void Reaccionar() { Console.WriteLine("La entidad se estremece."); }
}
class EntidadIris : Entidad {
    public override void Reaccionar() { Console.WriteLine("I.R.I.S corrompe el sistema."); }
}

Interfaces (Ejemplo complementario)

Las interfaces definen "qué" puede hacer un objeto, sin importar su herencia. Si en NEXUS quisiéramos que tanto un Objeto (ítems) como un Enemigo pudieran ser examinados, crearíamos un contrato IExaminable.

public interface IExaminable {
    string EscanearDatos();
}
class Objeto : IExaminable { /* Implementa el escaneo del item */ }
class Enemigo : Entidad, IExaminable { /* Implementa el escaneo biológico */ }

IV. Colecciones y LINQ

Listas genéricas y Colas

Los arreglos estáticos son limitados. NEXUS utiliza List<Objeto> Inventario porque el jugador constantemente craftea y descarta items dinámicamente. Además, usaste un diseño brillante para la IA enemiga mediante una Cola (Queue) FIFO:

Queue<EntidadIris> enjambreIris = new Queue<EntidadIris>();
enjambreIris.Enqueue(new EntidadIris("Cazador-Alfa"));
EntidadIris irisActual = enjambreIris.Peek(); // Analiza al enemigo sin sacarlo de la cola

Consultas LINQ y Expresiones Lambda (Ejemplo aplicado a NEXUS)

Actualmente NEXUS recorre el inventario usando bucles for clásicos. Si integráramos la librería LINQ (using System.Linq;), podríamos filtrar el inventario del cadete de manera declarativa usando una expresión Lambda (x =>). Así filtraríamos objetos para una anomalía de "Tiempo":

// Filtrado (Where): Extrae solo los objetos que sirvan para la anomalía de Tiempo
var objetosUtiles = cadete.Inventario.Where(x => x.Contrarresta == Anomalia.Tiempo).ToList();

// Transformación (Select): Obtiene solo los nombres en formato lista de strings
var nombresObjetos = cadete.Inventario.Select(x => x.Nombre).ToList();

// Ordenamiento (OrderBy): Ordena el inventario por usos restantes
var invOrdenado = cadete.Inventario.OrderBy(x => x.Usos).ToList();

V. Análisis del funcionamiento

1. Flujograma de Combate en NEXUS

[Input Cmd] → [Switch case 1/2/3/4] → [Aplicar Daño Enemigo] → [Enemigo Vida <= 0?] --(Sí)--> [Ganar Fragmento] --(No)--> [Turno Enemigo] → [Jugador Vida <= 0?] → [Apagar Simulación]

2. Seguimiento del estado en memoria (Heap vs Stack)

En el caso 1 de interacción de NEXUS, extraes un objeto de la lista para usarlo:

Objeto objUsado = cadete.Inventario[indiceUso - 1];
objUsado.Usos--;

Seguimiento: Al ejecutar objUsado.Usos--, el uso se descuenta directamente en el inventario real. ¿Por qué? Porque objUsado no es una copia aislada del objeto; es una variable en el Stack que apunta por referencia exacta al mismo espacio de memoria Heap donde reside la lista original.

3. Predicción de fragmento de código

Fragmento (Línea ~318 de Program.cs): cadete.Energia += 5; (Tras ganar minijuego).

Predicción: Si el EnergiaMax del cadete es 10, y actualmente tiene 9 de energía, al sumar 5 el valor pasaría a 14. Sin embargo, gracias a la propiedad Energia con setter restrictivo: set { _energia = value >= EnergiaMax ? EnergiaMax : (value < 0 ? 0 : value); }, la condición evalúa 14 >= 10. El resultado real es que la energía se trunca y se asigna exactamente a 10. Nunca superará el límite.

VI. Preparación para el examen H3

  1. ¿Por qué el constructor de Usuario incluye una versión vacía public Usuario() { } si el juego requiere nombre y edad?
    Respuesta: Porque NEXUS utiliza JsonSerializer.Deserialize para cargar la partida. El motor de serialización de .NET requiere instanciar la clase sin parámetros antes de inyectar las propiedades mapeadas desde el archivo JSON.
  2. En el método Asimilar de EntidadIris, el parámetro ref bool conectado se pasa con la palabra clave ref. ¿Qué significa estructuralmente?
    Respuesta: Los booleanos son tipos de valor (Value Types, se copian en el Stack). Al usar ref, le entregamos a la entidad IRIS la dirección de memoria de la variable original del Main. Si IRIS altera la variable a false, el bucle while (conectado) del Main colapsará inmediatamente, apagando el juego.
  3. Si quisieras que EntidadIris y Enemigo pudieran recibir daño usando el mismo método, ¿cómo modificarías la base Entidad?
    Respuesta: Se debe utilizar Herencia y Polimorfismo. Hacemos que EntidadIris herede de Entidad (actualmente no lo hace). Luego crearíamos un método public virtual void RecibirDaño(int d) en Entidad que ambos hijos pudieran sobreescribir (override).
  4. Analiza: var vivos = ListaRealidades.Where(r => !r.Extraida); ¿La lista resultante contiene copias nuevas de las realidades?
    Respuesta: No. Las consultas LINQ (y las Listas en general) almacenan referencias (punteros al Heap). vivos simplemente contiene un subconjunto de "enlaces" a las realidades originales. Alterar un objeto en vivos alteraría el objeto original en ListaRealidades.
  5. ¿Por qué AtlasRealidades tiene un constructor private AtlasRealidades() { }?
    Respuesta: Para implementar un patrón similar al Singleton / Static Class. Al ser privado, el compilador prohíbe que el Main ejecute new AtlasRealidades(). La clase existe solo como un servicio de utilidad global estático para renderizar el mapa multiversal.
  6. ¿Qué principio de POO se evidencia en la clase Enemigo donde Nombre tiene un private set?
    Respuesta: Encapsulamiento y mutabilidad controlada. El nombre del enemigo se define internamente en su propio constructor mediante un arreglo estático aleatorio. El exterior (el Main) puede leerlo (get público), pero es imposible que el jugador renombre a un enemigo externamente.
